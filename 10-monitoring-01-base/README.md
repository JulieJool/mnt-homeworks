# Домашнее задание к занятию 13 «Введение в мониторинг»

## Обязательные задания

1. Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя платформу для вычислений с выдачей текстовых отчётов, которые сохраняются на диск. 
Взаимодействие с платформой осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы выведите в мониторинг и почему?

**Ответ:**     
Минимум метрик следующий:    

<ins>Метрики производительности сервера</ins>                  
- Загрузка ЦПУ (CPU Usage, Load Average);     
- Использование памяти (Memory Usage);      
- Задержка (Latency) - имеется в виду время отклика на HTTP-запросы пользователей.     
<ins>Метрики взаимодействия</ins>            
- Количество запросов (Request Count) - общее число запросов, потенциальные пики активности;
- Saturation - длина очереди или время пребывания задач в очереди;
- Ошибки HTTP (HTTP Error Rate) - например, 4xx и 5xx - доступность и корректность работы API.        
<ins>Метрики работы с диском</ins>             
- Использование диска (Disk Usage);             
- Скорость записи/чтения (IOPS).            
<ins>Метрики состояния приложения</ins>           
- Время выполнения вычислений (Execution Time) - выявление медленных операций и их оптимизация;    
- Количество активных сессий или пользователей (Active Sessions/Users) - оценим загруженность системы.
При необходимости есть смысл оценить параметры безопасности (нетипичное кол-во авторизаций, аномальное кол-во запросов от от одного пользователя и т.д.).    


2. Менеджер продукта, посмотрев на ваши метрики, сказал, что ему непонятно, что такое RAM/inodes/CPUla. Также он сказал, что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы можете ему предложить?         

**Ответ:**     
Необязательно требовать от менеджера понимание терминалогии, правильнее будет обозначить комплексные бизнес-ориентированные метрики и показатели, они помогут нам установить четкие ожидания относительно уровня обслуживания, который предстоить предоставить клиентам:    
- SLA (Service Level Agreement) - документ, который описывает соглашение между поставщиком услуг и клиентом. Он определяет обязательства поставщика по предоставлению услуги и включает в себя конкретные параметры, которые будут измеряться. Может включать в себя описание услуг, конкретные метрики (доступность, время отклика и время восстановления), обязанности как поставщика услуг, так и клиента, штрафы и возмещение и прочее.    
- SLI (Service Level Indicator) - метрика, которая используется для измерения качества обслуживания. Это, как правило, количественный покзаатель, позволяет отслеживать, насколько хорошо сервис соответствует установленным ожиданиям. Может быть в качестве показателя доступности, времени отклика, процентом запросов, которые завершаются с ошибками.         
- SLO (Service Level Objective) - это конкретная цель/целевое значение для одного или нескольких SLI. Это значит, что SLO устанавливает уровень, который организация стремится достичь для обеспечения качества обслуживания. Например, SLO для показателя доступности - 99.9% времени в месяц, SLO для времени отклика - не должно превышать 200 мс для 90% запросов и другие.     


3. Вашей DevOps-команде в этом году не выделили финансирование на построение системы сбора логов. Разработчики, в свою очередь, хотят видеть все ошибки, которые выдают их приложения. Какое решение вы можете предпринять в этой ситуации, чтобы разработчики получали ошибки приложения?        

**Ответ:**     
В таком случае можно использовать скрипты, которые будут собирать ошибки и отправлять в нужный файл (логирование в файлы, в консоль), использовать по возможности syslog (если используется Linux оборудование) - здесь поможет правильная настройка cron/systemd для отправки ошибок по почте или в приложение, также использовать бесплатное оборудование (logwatch, grafana loki), использовать стек ELK (elasticsearch, kibana, logstash, filebeat). Можно даже попробовать использовать локальное логирование (контейнеры Docker с настроенными логами, которые легко можно проверять на локальных машинах). Для разработчиков можно настроить автоматическую отправку логов в репозиторий через Git в виде артефактов сборки или непосредственный сбор логов в системе CI/CD (при ее наличии) во время сборки и тестирования.      


4. Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA = 99% по http-кодам ответов. 
Этот параметр вычисляется по формуле: summ_2xx_requests/summ_all_requests. Он не поднимается выше 70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?        

**Ответ:**     
Скорее всего дело в недостаточно полном охвате запросов данной формулой. Здесь не учитывается количество кодов с ответами 3хх (перенаправление) и 1хх (продолжение кода сервера), которые не считаются за ошибку, но не включены в формулу, их количество следует добавить в числитель вместе с 2хх кодами, а также желательно оценить их отшение к общему числу запросов по отдельности.


## Дополнительное задание* (со звёздочкой) 

Выполнение этого задания необязательно и никак не влияет на получение зачёта по домашней работе.

_____

Вы устроились на работу в стартап. На данный момент у вас нет возможности развернуть полноценную систему 
мониторинга, и вы решили самостоятельно написать простой python3-скрипт для сбора основных метрик сервера. 

Вы, как опытный системный администратор, знаете, что системная информация сервера лежит в директории `/proc`. Также знаете, что в системе Linux есть планировщик задач cron, который может запускать задачи по расписанию.

Суммировав всё, вы спроектировали приложение, которое:

- является python3-скриптом;
- собирает метрики из папки `/proc`;
- складывает метрики в файл 'YY-MM-DD-awesome-monitoring.log' в директорию /var/log 
(YY — год, MM — месяц, DD — день);
- каждый сбор метрик складывается в виде json-строки, в виде:
  + timestamp — временная метка, int, unixtimestamp;
  + metric_1 — метрика 1;
  + metric_2 — метрика 2;
  
     ...
     
  + metric_N — метрика N.
  
- сбор метрик происходит каждую минуту по cron-расписанию.

Для успешного выполнения задания нужно привести:

* работающий код python3-скрипта;
* конфигурацию cron-расписания;
* пример верно сформированного 'YY-MM-DD-awesome-monitoring.log', имеющий не меньше пяти записей.

Дополнительная информация:

1. Количество собираемых метрик должно быть не меньше четырёх.
1. По желанию можно не ограничивать себя только сбором метрик из `/proc`.
